# Tool Authoring Guide

Conventions for **creating and editing** tools — naming, descriptions, input
and output shape, error handling, and code structure. This is the rulebook, not
a catalogue: for the live list of tools and their parameters, read
`src/tools/*.ts` or call `tools/list` on a running server.

The contract every tool upholds: **results are never guessed.** Everything below
serves that promise — precise validation, explicit errors, deterministic output.

---

## Naming & registration

- **One file per tool:** `src/tools/<name>.ts`. The kebab-case file name *is* the
  MCP tool name.
- **Export shape:** a regular tool exports `<camel>Tool` (a `ToolDef`); a tool
  that composes other tools exports `build<Camel>Tool(otherTools)` (a factory —
  this is how `script` reaches every other tool).
- **Registration is automatic.** `src/tools/registry.ts` is generated by
  `scripts/gen-registry.mjs` from the directory listing, so a new file in
  `src/tools/` is picked up the next time any `npm` script runs (the generator
  fires via `pre*` hooks). Don't hand-edit `registry.ts` — the drift test in
  `tests/registry-sync.test.ts` enforces that. See
  [DEVELOPMENT.md](DEVELOPMENT.md#adding-a-tool) for the full new-tool checklist.
- **`name`:** lowercase kebab-case, a short noun or verb (`hash`, `convert-data`,
  `json-query`). Unique. Conformance enforces `^[a-z][a-z0-9-]*$`.
- **`title`:** a short human-readable label (`"Hash / HMAC"`, `"DNS lookup"`).

## Descriptions — the LLM picks your tool from these

The description is the single most important field: it's how a model decides
whether and how to call the tool. Write it for that reader.

- Lead with **what it does and when to reach for it.**
- State the **guarantees**: deterministic and offline, or exactly which paths
  touch the network.
- Enumerate the **operations** (`action`/`format`/`kind` values) and any
  **non-obvious semantics** — units, what's auto-detected, what's rejected, edge
  behaviour.
- Be **accurate**. A capability you describe but don't implement (or vice versa)
  is a bug — a caller follows the docs and hits an error or silent wrong result.
  Keep the tool's `description`, this guide's conventions, and any matching prose
  in `docs/` in sync in the same change.
- Minimum 40 characters (conformance), but a real description is a few sentences.

## Inputs

- **Discriminate, don't multiply.** One tool with an `action`/`format`/`kind`
  enum beats many near-identical tools. Declare a `refine(args, ctx)` on the
  `ToolDef` for action-specific / cross-field rules — `server.ts` threads it
  into a `superRefine` so the caller gets a precise error at the schema boundary
  *before* the handler runs. The handler must still enforce the same rule as a
  value (it's also invoked directly by the `script` gateway and unit tests,
  which bypass the boundary schema), so `refine` is the boundary guard, not the
  only one.
- **Parameter naming.** `input` / `inputUrl` for data the tool *transforms*;
  `value` / `host` / `url` for a *target* it looks up. Rename to fit rather than
  carrying aliases (early-alpha); if a rename is unavoidable, add a `superRefine`
  that points the caller at the new name.
- **Binary.** Offer `inputEncoding` / `outputEncoding` (`utf8` / `base64` /
  `hex`) wherever binary data is plausible, so tools chain. Exception: a tool
  with two distinct byte streams may use domain-specific names — e.g. `http`
  uses `requestBodyEncoding` / `responseEncoding` + `responseBodyEncoding`
  because one `inputEncoding`/`outputEncoding` pair can't name both the request
  and response bodies.
- **Remote input.** Document-shaped tools accept `inputUrl` (or `aUrl` / `bUrl`)
  as an opt-in alternative to inline input, resolved by the shared
  `src/lib/input.ts` fetcher (GET, 10 s, 5 MB, SSRF-guarded). Network never
  happens unless the caller passes a URL.
- **Batch.** Where it's natural, accept an array for the primary input (opt-in
  per tool) — see the batch output rule below.
- **Defaults live in the Zod schema** (so the handler always receives them). The
  schema is strict: unknown keys are rejected at the boundary, not silently
  dropped.

## Outputs

- **Two representations, always.** Return a readable `content` text block *and*
  machine-readable `structuredContent`. Declare an `outputSchema` when the
  result has a **stable shape** (e.g. `http`, `diff`, `convert-data`,
  `json-query`, `script`) — the SDK validates `structuredContent` against it, so
  a tool whose output varies per `action`/`kind` (e.g. `inspect`, `time`, `net`)
  is better left without one than forced into a brittle discriminated union that
  must track every branch or the call fails.
- **JSON-serialisable.** No `BigInt`, no circular refs — represent huge integers
  as decimal strings (cf. `net` host counts). Conformance asserts this.
- **Batch envelope.** Array input returns `{ results: [...], failures: [...] }`
  with `failures` **always present** (empty array when nothing failed) and
  **per-item isolation** — one bad item lands in `failures`, the good ones still
  return. Failure entries are `{ index, value, error }`.
- **Empty ≠ failed.** "no records" / "no match" is a *successful* empty result,
  distinct from "the lookup failed."
- **Add the convenience field.** Surface computed values a caller would otherwise
  re-derive (`daysRemaining`, `ageInDays`, `isoUtc`), so they don't have to.

## Errors

- **Errors are values.** Return them via the `err()` helper (`isError: true`,
  message prefixed `Error: `). **Never throw** from a handler; never let a
  library-internal trace leak; never silently coerce or guess on bad input.
- **Be precise and actionable** — `"invalid base64 at offset 17"`, point at the
  fix. Reject ambiguous input rather than picking an interpretation.
- **Validate at the layer you own:** the schema rejects shape / enum /
  unknown-key problems; the handler rejects semantic ones.

## Code structure — keep the tool file thin

- **A `ToolDef` is glue.** Its job is: validate/destructure args → dispatch on
  the discriminator → call into `lib/` → format the result. It should read in one
  glance.
- **Real logic lives in `src/lib/*`** — pure, independently unit-testable
  functions that know nothing about MCP or the `ToolDef` shape (radix, base32,
  jsonpath, units, cert, colour, net, whois/rdap, …). Tests hit the lib directly.
- **No massive handlers or helpers.** If a function outgrows a screen, split it.
  One concern per function.
- **Encapsulate complex branching.** A long `if`/`switch` ladder becomes a named
  helper or a lookup/dispatch table — favour small, descriptively-named functions
  over inline cleverness. The reader should follow the flow without holding the
  whole branch tree in their head.
- **Prefer an in-house `lib/` helper over a new dependency** when it's small and
  self-contained (base32, crc32, radix, jsonpath, units are all in-house). New
  runtime deps need a reason — see the dependency budget in
  [ARCHITECTURE.md](ARCHITECTURE.md).

## Determinism

- **Pure and deterministic by default** — same input, same output. The
  conformance suite asserts byte-identical output across repeated calls.
- The network / clock / CSPRNG tools are the explicit exceptions; keep that
  non-determinism isolated to the tool whose job it actually is.
