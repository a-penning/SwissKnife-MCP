Design Proposal · SwissKnife MCP

Proposal: crypto tool

Status: Design proposal — not yet implemented. Nothing in this file describes shipped behaviour.

A general-purpose cryptographic primitive tool: symmetric AEAD, asymmetric encryption / signing / key generation, password-based and key-based derivation, key-format conversion, and OpenPGP. Eight actions. Where an operation has variants, method takes the algorithm name directly ("aes-256-gcm", "rsa-oaep", "ed25519", "pgp", …) — no abstract "symmetric" / "asymmetric" layer, no parallel algorithm field.

Why this tool

SwissKnife's existing crypto surface is fragmentary: hash does digests and HMAC, jwt does one signed-token format, id generates passwords and UUIDs. There is no way to encrypt or decrypt arbitrary data, generate a keypair, sign or verify outside the JWT envelope, derive a key from a password, convert keys between formats, or work with OpenPGP at all.

These are the operations an LLM is most likely to hallucinate without a tool — wrong nonce sizes, made-up base64 ciphertexts, invented PGP fingerprints. The script VM cannot fill the gap: it is sandboxed without node:crypto or WebCrypto, so encryption is genuinely unreachable from user code. Primitive-capability gap, not an ergonomic one.

OpenPGP is current and load-bearing in 2026 — Git commit signing, release-artifact verification (.asc on tarballs, npm/PyPI provenance), distro package signing, pass-based secret management, SOPS-encrypted secrets in Git. The user-facing primitives are the same shape whether the envelope is raw or PGP, so PGP rides on the existing actions via method: "pgp" rather than splitting its own.

MCP description (what the LLM sees)

This is the description string the tool ships with — the single most important field, because it's how a model decides whether and how to call the tool (per docs/TOOLS.md). Every supported method is listed here with its required parameters and defaults. Anything not listed isn't reachable — there's no hidden fallback path.

General-purpose crypto primitives. Eight actions. Where an operation has variants, `method` names the algorithm directly — no separate `algorithm` field. encrypt — produces ciphertext. "aes-256-gcm" (default) / "aes-128-gcm" / "chacha20-poly1305" — AEAD. Needs `key`, `plaintext`; auto-generates 12-byte `nonce` unless supplied; optional `aad`. Reusing a (key, nonce) pair on GCM catastrophically breaks confidentiality. "rsa-oaep" — needs `publicKey`, `plaintext`; `oaepHash` default "sha256"; plaintext capped by modulus. "pgp" — needs `message` plus `recipients` (array of PGP public-key blocks) OR `passphrase` (symmetric). Optional `signingKey` + `signingPassphrase`, `armor` (default true), `preferredCipher`. decrypt — mirrors encrypt's methods (swap public/private, swap ciphertext/plaintext). All failure modes return `decryption_failed` — single bucket; failure mode isn't leaked. sign — produces a detached signature. "ed25519" / "ecdsa" / "rsa-pss" (default for RSA) / "rsa-pkcs1" (legacy). Needs `privateKey`, `message`; `hash` default "sha256". "pgp" — needs `privateKey`, `passphrase`, `message`. Optional `type`: "detached" (default) / "cleartext" / "inline". verify — failure → `{valid: false}`, NOT an error. Asymmetric: needs `publicKey`, `message`, `signature`. "pgp" — needs `signature` plus `publicKeys` OR `keyserverUrl` (HKPS/VKS, SSRF-guarded). Detached also needs `message`. Refuses SHA-1 / MD5 signatures unless `acceptLegacyHash: true`. generate "bytes" — random symmetric bytes; needs `byteLength`. "rsa" / "ec" / "ed25519" (default) / "x25519" / "secp256k1" — raw keypair. RSA: `modulusLength` (default 3072). EC: `curve` (P-256/384/521). "pgp" — OpenPGP keypair; needs `userIds`, `passphrase`. Defaults Ed25519+X25519, v6 keys, no expiry. derive "argon2id" (default) / "scrypt" / "pbkdf2" — password-based. Needs `password`, `keyLength`; auto-generates `salt` (always returned). "hkdf" — from key material; needs `ikm`, `keyLength`; optional `salt`, `info`. "ecdh" — agreement (X25519 / ECDH-P256/384/521). Needs `privateKey`, `peerPublicKey`. Output is raw shared secret — chain with hkdf before use. inspect — auto-detects input (PEM, DER, JWK, PGP armored, PGP binary via inputEncoding:"base64"). Returns type, fingerprint, expiry, user IDs, subkeys. Public metadata only; never echoes private material. convert — raw key format conversion: PEM ↔ DER ↔ JWK. Auto-detects `from`; `to` is explicit. PGP keys don't participate. Anything not listed returns `unsupported_algorithm`. Notable refusals: AES-CBC/CTR (no AEAD), RSA-PKCS1-v1_5 encryption, MD5/SHA-1 for new signing. Private keys and passphrases passed in are never echoed back. Private material is only returned by `generate` and `convert`. All randomness from OS CSPRNG.

(This is the design's view of the description; the implementation will replicate it verbatim in src/tools/crypto.ts. A drift test in tests/conformance.test.ts can pin the two together if useful.)

Action surface

Eight actions. Method values listed by action below — each value pins exactly one parameter shape (Zod discriminatedUnion at the schema boundary).

Actionmethod valuesPurpose
encrypt aes-256-gcm · aes-128-gcm · chacha20-poly1305 · rsa-oaep · pgp Produce ciphertext.
decrypt same set as encrypt Recover plaintext.
sign ed25519 · ecdsa · rsa-pss · rsa-pkcs1 · pgp Produce a detached / cleartext / inline signature.
verify same set as sign Verify a signature. Failure → {valid: false}, not an error.
generate bytes · rsa · ec · ed25519 · x25519 · secp256k1 · pgp Produce key material.
derive argon2id · scrypt · pbkdf2 · hkdf · ecdh Derive a key from a password, key material, or DH agreement.
inspect — Auto-detect input format and describe (PEM, DER, JWK, PGP armored, PGP binary).
convert — Raw asymmetric key format conversion (PEM ↔ DER ↔ JWK).

No outputSchema — the result shape varies per action and method; a discriminated-union schema would have to track every branch.

Key handling

Accepted input formats

  • PEM: PKCS#1, PKCS#8, SEC1, SPKI, X.509-certificate-as-public-key-source.
  • DER: same containers, base64-encoded via standard inputEncoding semantics.
  • JWK: JSON object — RSA / EC / OKP types.
  • Raw symmetric keys: bytes via inputEncoding (base64 / hex / utf8).
  • OpenPGP armored: -----BEGIN PGP PUBLIC KEY BLOCK----- / PRIVATE KEY BLOCK / MESSAGE / SIGNATURE / SIGNED MESSAGE.
  • OpenPGP binary: raw packet stream via inputEncoding: "base64".

Output formats

Explicit, never auto-chosen. PEM is the default for raw-key crypto output; JWK is supported for everything except raw symmetric. For PGP, armor: true (default) yields ASCII-armored output; armor: false yields raw packets returned as base64.

Redaction

  • Private material passed into the tool is never echoed in any response.
  • Private material is returned only by generate and convert.
  • inspect returns metadata only — even if the input was a private key, the response describes public material plus an isPrivate flag.
  • PGP passphrases passed in are never echoed back, even on error.
  • The MCP description states this so callers don't pipe output through anything that logs verbatim arguments.

Error model

Errors are err() values, per docs/TOOLS.md.

CodeMeaning
invalid_keyParse failed, wrong type, unsupported curve.
wrong_algorithmKey type does not match requested method (e.g. Ed25519 key with method:"ecdsa").
decryption_failedSingle bucket for all decryption failures — bad tag, wrong key, wrong nonce, tampered ciphertext, wrong AAD, wrong passphrase.
unsupported_algorithmRequested method / algorithm isn't on the supported list.
bad_parametersKDF cost outside allowed range, key length wrong for method, nonce wrong size, RSA-OAEP plaintext exceeds modulus.
too_largeInput exceeds the configured cap.
parse_failedGeneric format-parse failure not covered above.
pgp_key_expiredEncryption / signing requested with an expired key.
pgp_key_unavailableVerification needed a key not supplied and not found via the keyserver.
keyserver_fetch_failedHTTP error / timeout / SSRF-block reaching the keyserver URL.

Verification failure on verify is not an error — it's { valid: false }. Same model as jwt verify.

Security posture

  • Randomness: OS CSPRNG only, via node:crypto.randomBytes. No userspace PRNG, no seeded random.
  • Nonce policy: auto-generated by default for AEAD. Caller-supplied nonces accepted; the MCP description warns explicitly about GCM nonce reuse.
  • Constant-time comparisons for signature verification and AEAD authentication tags — crypto.timingSafeEqual, never ===.
  • No fallback algorithm negotiation. The caller specifies the method; we don't pick one based on key type unless exactly one valid choice exists for that key.
  • No silent downgrades. A request for method:"aes-128-gcm" with a 32-byte key is bad_parameters, not "we'll just truncate."
  • AEAD only for symmetric encryption. No raw block-cipher or stream-cipher modes without authentication.
  • RSA encryption is OAEP only. No PKCS1-v1_5 encrypt — padding-oracle history.
  • PGP legacy-hash policy. SHA-1 / MD5 PGP signatures fail verification by default; acceptLegacyHash: true opts in per call. Signing with SHA-1 / MD5 is never permitted.
  • PGP expiry enforcement. Encrypting to / signing with an expired key is pgp_key_expired. Verifying a signature made before the signing key's expiry is still considered valid (signature-was-valid-at-time-of-signing); response surfaces keyExpiredAfterSigning: true.
  • Keyserver fetches are SSRF-guarded via the same path as jwt's JWKS-URL fetch — see src/lib/ssrf.ts.
  • No private-key-in-logs surface. Tool response never contains private material the caller passed in; conformance asserts this across every (action, method) combination.

Implementation notes

Dependencies

Most paths are node:crypto (Node 22 LTS): AES-GCM, ChaCha20-Poly1305, RSA-OAEP, PBKDF2, scrypt, HKDF, RSA / EC / Ed25519 / X25519 keygen, sign / verify, ECDH / X25519 agreement, PEM ↔ DER ↔ JWK.

PackagePurposeNotes
openpgp (v6+)All method: "pgp" paths.Pure JS, RFC 9580 (2024) + RFC 4880 (v4) compliant, ProtonMail-maintained, tree-shakable. ~500 KB unpacked.
@node-rs/argon2derive method:"argon2id".Native (NAPI) with prebuilt binaries. Chosen over argon2 (node-gyp, breaks Docker), and over hash-wasm (~5× slower).

Alternatives rejected for PGP: shelling out to system gpg (drags in keyring / agent / GNUPGHOME, exactly the statefulness the suite forbids; needs the binary at runtime, breaks npx/Docker), and rolling our own (RFC 9580 too large to reimplement responsibly).

script integration

crypto is wired into the script VM the same way every other tool is — via the build*Tool factory pattern. Example: fetch a release tarball via http, fetch its .asc via http, then verify method:"pgp" in one script run. ECIES-style hybrid encryption: generate method:"x25519" → derive method:"ecdh" → derive method:"hkdf" → encrypt method:"aes-256-gcm" in a single script. The VM still cannot perform crypto itself; everything goes through this tool.

Test strategy

Per docs/TESTING-STRATEGY.md:

  • Independently derived vectors. RFC test vectors (RFC 7539 ChaCha20-Poly1305, RFC 8017 RSA-OAEP, RFC 8032 Ed25519, RFC 6070 PBKDF2, RFC 7914 scrypt, RFC 9106 argon2, RFC 5869 HKDF, RFC 9580 OpenPGP), not output pasted from the implementation under test.
  • Round-trip properties. For every (action, method) combination: decrypt(encrypt(plaintext)) === plaintext; verify(sign(message)) === true; convert(convert(key, a→b), b→a) === key; inspect(generate(...)) reports the expected type and fingerprint.
  • Real-world fixtures. A Debian Release.gpg, a tagged Git commit's GPG signature, a published npm provenance manifest. Verification of these keeps us honest against the gap between RFC vectors and what GPG actually emits.
  • Negative cases. Wrong key → decryption_failed. Tampered ciphertext / AAD → decryption_failed. Wrong key type for method → wrong_algorithm. Refused method → unsupported_algorithm. Expired PGP key on encrypt → pgp_key_expired. SHA-1 PGP signature without acceptLegacyHash → { valid: false, reason: "weak_hash" }. RSA-OAEP plaintext exceeding modulus → bad_parameters.
  • Redaction conformance. Registry-driven sweep across every (action, method) that accepts a private key or passphrase; asserts the secret never appears in the response.
  • Cap enforcement. At-cap passes; over-cap fails predictably.
  • Inspect auto-detect. Table-driven across every supported input format; assertions for correct dispatch.
  • Composed hybrid encryption. The documented ECIES-equivalent recipe (generate → derive ecdh → derive hkdf → encrypt aes-256-gcm) round-trips.
  • Keyserver fetch. Mocked HTTP layer; verifies SSRF guard path is taken.
  • Description drift. A test pins the source-of-truth description in crypto.ts to the one in this proposal — they must stay aligned.

Open questions

  1. secp256k1 sign/verify. Node supports keygen; signature operations have edge cases (low-S enforcement for Ethereum). Ship without ECDSA-on-secp256k1 in v1?
  2. Streaming. Every existing tool is one-shot. Defer until someone has a real use case — script's 30 s budget and the 16 MiB cap cover most needs.
  3. Algorithm name canonicalisation. Should aes256gcm, AES-256-GCM, aes-256-gcm all parse? Lean strict (one canonical form). Saves owning a normalisation table.
  4. JWK thumbprint format. RFC 7638 canonical thumbprint, base64url-encoded. inspect should return one even for non-JWK input — universal key fingerprint.
  5. PGP keyserver protocols. Support both VKS (keys.openpgp.org) and the older HKP/HKPS family, or only VKS?
  6. PGP v6 vs v4 default. Both supported by openpgp.js. Default v6 for new generate method:"pgp" calls; confirm.
  7. Cleartext signature normalisation. Cleartext PGP signatures normalise line endings before hashing (dash-escape, trailing-whitespace strip). Document this in the description.

Rollout

Ship as one piece — all eight actions across every method, implemented and tested together. Two new dependencies: openpgp and @node-rs/argon2. No staged release.
